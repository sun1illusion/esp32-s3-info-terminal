## 踩坑记录

每条按「现象 → 根因 → 处置」写，都是花时间最多的那些。

### 1. OLED 初始化直接 Double exception 崩溃

**现象**：调用 OLED 初始化就重启，串口打印 `Double exception`，栈指针指向非法地址。

**根因**：SSD1306 显存 512 字节，代码把整块拷进了一个 **129 字节的栈缓冲**。栈溢出踩掉了返回地址和好几层栈帧。

**处置**：按 I²C 单次传输上限，分 128 字节循环发送：

```c
for (int i = 0; i < 512; i += 128) {
    i2c_master_transmit(dev, &buf[i], 128, timeout);
}
```

**教训**：`memcpy` 到栈缓冲没有任何边界检查，编译器不会警告，崩溃位置还跟真凶无关。

---

### 2. 本模组 PSRAM 不可用

**现象**：开启 `CONFIG_SPIRAM` 后随机出错——偶尔崩溃，更多是数据静默错误。

**根因**：所用模组是 **v0.2 芯片版本**，片外 RAM 接口存在已知缺陷。

**处置**：`CONFIG_SPIRAM` 永久关闭。后续所有内存决策都是这个约束推出来的。

**影响**：只能用内部 SRAM，约 320KB。这直接导致了绘图缓冲调优、字库裁剪和整套内存诊断机制。

---

### 3. LVGL 池从 64KB 缩到 56KB，跑到第 60 秒崩溃

**现象**：改小 `CONFIG_LV_MEM_SIZE` 后，开机正常，跑一分钟左右崩溃。短测看起来完全健康。

**根因**：LVGL 的峰值用量出现在**渲染**阶段，不是创建阶段。短测只测了创建，用量小得多。第一次完整渲染周期跑完，池子就不够了。

**处置**：测峰值再留余量。现在是 72KB 池配 52KB 峰值。

**教训**：初始化完读到的内存数字不是峰值。峰值出现在第一次重负载操作——整屏重绘、TLS 握手、大 JSON 解析。

---

### 4. 缺字只画空白框，一声不吭

**现象**：新加的界面文字位置是个空方框，日志里什么都没有。LVGL 不认为这是错误。

**根因**：点阵字库是按**生成那一刻**源码里出现的字符生成的。之后新增的文字根本不在字库里。

**处置，两层**：

- **编译期**：`tools/check_glyphs.py` 扫描所有字符串字面量报出缺失码点，`tools/regen_font.py` 按「已有码点 ∪ 新用到的字」重新生成
- **运行时**：`Diag_CheckGlyphs()` 在初始化后遍历每个页面的每个 `lv_label`，用 `lv_font_get_glyph_dsc()` 逐字符确认字形是否存在，缺失就打出码点

```
I (734)  font: 【主页】字库完整
E (xxx)  font: 【系统监控】缺字 U+8D1F
```

这个坑踩了**两次**（「占」和「负」）才加的运行时检查。教训是：库静默失败时，该加断言，而不是靠记性。

---

### 5. OTA 返回 200，但设备还是老固件

**现象**：上传固件成功，浏览器显示 ok，设备重启——然后起来还是旧版本。

**根因**：不是 OTA 的 bug。直接读 `otadata` 才看明白：

```
sector0: seq=3 state=4 (ABORTED)   ← 新分区被否决
sector1: seq=2 state=2 (VALID)     ← 回退到这个
```

镜像确实写对了、也标记启动了。但验证阶段用的串口抓取脚本**会拉 RTS 复位芯片**，而它是在 30 秒确认窗口内运行的——新固件还没来得及调 `esp_ota_mark_app_valid_cancel_rollback()` 就被复位，Bootloader 判定"启动失败"，标记 `ABORTED` 并回滚。

**处置**：上传后等 35 秒再开串口，或者先查 `/api/sys` 的 `part` 字段。

**这次意外证明了什么**：回滚机制是真的有效。一个自己起不来的固件——不管什么原因——会被自动拒绝，设备不插线也能继续用。

---

### 6. 绘图缓冲减少，帧率居然不变

**现象**：以为从 60 行降到 40 行会掉帧，实测一模一样，都是 16fps。

**根因**：瓶颈不在 SPI 传输。LVGL 按 33ms 周期刷新（`CONFIG_LV_DEF_REFR_PERIOD`）。整帧 240×320×2 = 153600 字节，40MHz 下要 30.7ms，已经贴着周期上限。切成 6 块还是 8 块，总字节数不变。

测法是自己写的探针：铺一张全屏矩形做 HSV 颜色循环，强制每帧整屏重绘，用 `LV_EVENT_REFR_READY` 数完成次数。

> **为什么不用 SPI 的 `on_color_trans_done` 回调统计？** 那个回调已经被 `esp_lvgl_port` 注册用于同步 flush，再注册一个会覆盖掉它，直接花屏。

---

### 7. SNTP 在拿到 IP 之前启动，静默失败

**现象**：Wi-Fi 连上了，但时间一直停在 1970 年，日志没有任何报错。

**根因**：SNTP 在 `WiFi_Init()` 里就启动了，那时还没有 `IP_EVENT_STA_GOT_IP`。首个请求没有源地址，发出去就失败。而 lwIP 在这条路径上的重试间隔是**一小时**，所以看起来像是完全没反应。

**处置**：把 SNTP 启动挂到 `IP_EVENT_STA_GOT_IP` 回调里，不在初始化时启动。

---

### 8. GPIO 自检把好引脚报成坏的

**现象**：引脚完好性检查（输出电平再读回）总是读到 0，每个脚看起来都坏了。

**根因**：配置成了 `GPIO_MODE_OUTPUT`。这个模式下输入通路是关的，读回必然为 0。

**处置**：改用 `GPIO_MODE_INPUT_OUTPUT`，读回才是真实焊盘电平。

---

### 9. 「CPU 占用」那一列显示 IDLE 97%，把所有人都看懵了

**现象**：系统监控页列出 `IDLE0 97%`，读起来像"CPU 忙了 97%"，但事实正好相反。

**根因**：那个百分比是**任务自己占的 CPU 份额**。空闲任务跑了 97%，意思是 CPU **空闲 97%**。把它和普通任务并排列出来，语义完全反了。

**处置**：列表里过滤掉空闲任务，顶部单独给一个 **CPU 负载**，按 `100% − 平均空闲占比` 算。

**相关**：双核芯片上所有任务占比加起来会超过 100%。`uxTaskGetSystemState` 的 `total_run` 是墙上时间，两个核并行跑，各任务份额累加约等于 200%。单个任务仍然不超过 100%。

---

### 10. 短按有时候唤不醒屏

**现象**：加了息屏功能后，偶尔碰一下屏幕不亮。

**根因**：唤醒条件原本是每秒检查"当前是否按下"。快速点一下可能整个按下和抬起都发生在两次轮询之间。

**处置**：按下时记录时间戳，检测**时间戳是否变化**，而不是采样当前状态：

```c
if (last_press_ms != seen_ms) { wake(); }
```

---

### 11. 改分区表之后必须全片烧写

**现象**：从单个 `factory` 分区改成 `otadata` + 双 OTA 分区后，只烧应用固件，设备起不来。

**根因**：Bootloader 在 0x8000 读分区表。只烧应用不会更新分区表，也不会更新 `otadata`，更不会更新那个支持回滚的 bootloader。

**处置**：`bootloader.bin`(0x0)、`partition-table.bin`(0x8000)、`ota_data_initial.bin`(0xF000)、应用(0x20000) 一起烧——`idf.py flash` 就是这么干的。动分区表之前先做了 16MB 全片备份，出问题就整片恢复。

## 由此建立的诊断体系

这些坑最后沉淀成了一套工具，而不是一次性修修补补：

| 工具 | 作用 |
|---|---|
| `[diag]` 周期日志 | 堆空闲 / 最大块 / 最低水位 / LVGL 池 / 碎片率 |
| `[font]` 启动自检 | 逐页报出字库缺失的字符码点 |
| `APP_GPIO_SELFTEST` | 区分引脚击穿 / 缺上拉 / 模块没供电 |
| `APP_FPS_PROBE` | 强制整屏重绘测真实帧率 |
| `tools/check_glyphs.py` | 编译前静态检查字库覆盖 |
| `tools/regen_font.py` | 按实际源码用字重新生成点阵字库 |
| `tools/serial_capture.py` | 通过控制 RTS 抓取完整启动日志 |
