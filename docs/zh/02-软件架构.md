## 一、分层设计

```
┌──────────────────────────────────────────────┐
│  UI 层         ui_home / ui_weather /        │
│                ui_settings / ui_net /        │
│                ui_wifi / ui_sysmon           │
├──────────────────────────────────────────────┤
│  应用层        app_io     GPIO 抽象          │
│                app_ota    OTA 状态机         │
│                app_sysinfo 内存/任务数据     │
│                app_screen   息屏管理         │
│                app_diag     内存与字库自检   │
├──────────────────────────────────────────────┤
│  网络层        net_wifi / net_time /         │
│                net_weather / net_web         │
├──────────────────────────────────────────────┤
│  驱动层        board_lcd / board_touch /     │
│                board_oled / board_backlight /│
│                board_audio                   │
├──────────────────────────────────────────────┤
│  ESP-IDF       FreeRTOS / LVGL / lwIP / NVS  │
└──────────────────────────────────────────────┘
```

依赖是单向的：**UI 层不碰寄存器，驱动层不知道业务**。`board_lcd.c` 不知道天气页的存在，`ui_weather.c` 也不知道屏幕是 ILI9341。

## 二、任务设计

| 任务 | 优先级 | 核 | 创建方 | 职责 |
|---|---|---|---|---|
| `wifi` | 23 | 0 | ESP-IDF | 802.11 状态机，硬实时，绝不能饿着 |
| `ipc0` / `ipc1` | 24 | 0 / 1 | ESP-IDF | 核间调用处理 |
| `sys_evt` | 20 | 0 | ESP-IDF | 系统事件分发（`esp_event` 回调跑在这里） |
| `esp_timer` | 22 | 0 | ESP-IDF | 高精度定时器回调 |
| `httpd` | 5 | 任意 | ESP-IDF | HTTP 服务，一次处理一个连接 |
| `taskLVGL` | 5 | **1** | `esp_lvgl_port` | 渲染与触摸轮询，30ms 周期 |
| `weather` | 3 | 任意 | 应用 | 一次性 HTTPS 拉取，完成即退出 |
| `wifi_scan` | 3 | 任意 | 应用 | 一次性扫描，按需创建 |
| `main` | 1 | 任意 | 应用 | 初始化完成后长期阻塞 |
| `IDLE0` / `IDLE1` | 0 | 0 / 1 | FreeRTOS | 空闲任务，回收已删除任务的栈、喂任务看门狗 |

**为什么 LVGL 绑 Core1**：Wi-Fi 协议栈在 Core0。渲染加 SPI 传输是 CPU 密集型，和协议栈挤在同一个核会在整屏重绘时丢包、掉线。

**为什么不用队列**：应用层任务之间传递的是几个标量状态标志（`g_wifi_connected`、`g_brightness`）。Xtensa 上 32 位对齐的读写是原子的，`volatile` 变量加事件回调就够，上队列只会多一次拷贝和同步开销。如果出现生产消费速率不匹配——比如 100Hz 采集配一个慢速上传任务——那就必须用队列，架构也该跟着改。

## 三、内存预算

应用可用堆约 **320KB** 内部 SRAM。

| 占用方 | 大小 | 说明 |
|---|---|---|
| LVGL 内存池 | 72KB（可用 66KB） | 对象、样式、动画、文本缓冲 |
| 绘图缓冲（双缓冲） | 37.5KB | 240 × 40 × 2 字节 × 2 |
| Wi-Fi + lwIP 协议栈 | 约 40~60KB | `WiFi_Init()` 时分配 |
| 字库（占 Flash，不占 RAM） | — | `myfont_16.c` 是 `const`，待在 Flash |
| **全部启动后的空闲** | **88KB** | 最大连续块 31KB |

真正关键的是**最大连续块**而不是总空闲。TLS 握手需要约 16KB **连续**内存，总空闲看着有 88KB 很健康，一旦碎片化导致最大块不够，HTTPS 照样失败。

这也是固件每 10 分钟打这行日志的原因：

```
diag: RAM free=88KB 最大块=31KB 水位=40KB | LVGL池 free=14KB 峰值=52KB/65KB 碎片3%
```

（`水位` = 历史最低空闲堆，硬件级记录，采样频率再稀也不会漏掉谷底。）

## 四、关键设计决策

### 4.1 绘图缓冲取 40 行而不是 60 行

| 配置 | 缓冲占用 | 帧率 |
|---|---|---|
| 60 行 | 57.6KB | 16 fps |
| 40 行 | 37.5KB | **16 fps** |

省了 18.75KB，帧率一点没掉。瓶颈是 `CONFIG_LV_DEF_REFR_PERIOD = 33ms`（LVGL 刷新周期），不是 SPI 传输：整帧 153600 字节在 40MHz 下要 30.7ms，已经贴着周期上限。切成 6 块还是 8 块，总字节数不变。

### 4.2 所有页面一次建好，从不销毁

切页就是 `lv_scr_load()`。按需创建会带来分配延迟和堆碎片；九个页面同时存在时峰值 52KB，池子 66KB 够用。如果页面数量继续增长，这是第一个要改的地方。

### 4.3 自建中文字库，按实际用字裁剪

LVGL 内置字体不含 CJK 字形。为了避免塞进整套两万多字形（几 MB），这里生成了一套 16px 点阵字体，只包含源码里实际用到的字符——目前 **296 个码点**，作为 `.c` 数组约占 1MB Flash。

代价是：新增中文文案必须重新生成字库。这个流程已经自动化（`tools/check_glyphs.py` 检测缺字，`tools/regen_font.py` 重新生成），固件在启动时还会做一次**运行时检查**——LVGL 遇到缺字只会画个空白框、什么也不报，所以启动后遍历每个页面的每个 label，把缺失字符的码点打出来。

### 4.4 LVGL 的线程安全

LVGL 不是线程安全的。任何非 LVGL 任务的调用都必须包在锁里：

```c
lvgl_port_lock(0);
Home_Init();
lvgl_port_unlock();
```

不加锁的话，两个任务并发调 `lv_malloc` 会把 TLSF 的元数据写坏，崩溃位置看起来和真正的 bug 毫无关系。

`lvgl_port_lock` 是**递归**互斥量，所以定时器回调（本身已运行在 LVGL 任务上下文）再调一次不会死锁。

### 4.5 息屏策略

30 秒无触摸关闭背光，触摸立即恢复。

刻意**不**用 light sleep：那会断掉 Wi-Fi，对看板类设备意味着天气停止更新、远程控制失联，唤醒还要重连 3~5 秒。只关背光就能砍掉最大的一项功耗（100~150mA），而设备全程在线。

背光关闭期间触摸控制器仍在轮询——这是"摸一下就亮"能成立的前提。
